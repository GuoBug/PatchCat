## 1. 核心演进与人机协同思考

在 PatchCat 推进到 `v0.5.0` 的过程中，项目迎来了从“静态单向 DAG 提示词流水线”向“具备自主推理与反思能力的 Agent 智能体”的关键跃迁。

整个功能演进全程贯穿着**人机协同与双向启发（Milestone Co-Discovery）**的研发模式，而不是被动解决报错：
- **人提的关键点（业务场景与直觉）**：
  - 如果为了支持循环而在画布层级强行画“回流连线（Back-edges）”，会导致用户的连线复杂度呈指数级爆炸，画布迅速沦为无法维护的“意面式图谱（Spaghetti Graph）”；
  - 必须将 Agent 的核心循环收敛在单个独立的智能体节点内部，既保留全局 DAG 拓扑的高可观测性与并行波次调度优势，又能赋予节点自主决定工具调用的弹性；
  - 智能体需要具备把画布上已有节点（如配置好的知识库或复杂转换代码）作为“现成工具”调用的组合能力。
- **AI 提的关键点（工程规约与系统隐患）**：
  - 流式 Server-Sent Events (SSE) 下的 `tool_calls` 是分块碎片化传输的，不同模型服务商在参数流式输出时的序列化规则存在差异，必须在底层设计独立的多键累加器以保障参数拼装完备；
  - 智能体在面对模糊或矛盾任务时，存在持续反复调用同一无效工具产生“幻觉死循环”的重大隐患，必须引入具备严格上限的 `maxIterations` 熔断守卫与中断信号透传。

## 2. 边写边学与方案权衡 (Trade-offs & Learning)

在构建 ReAct（Reason + Act + Observe）循环时，团队对比了三种实现形态：

| 架构选型 | 优势 | 弊端与工程代价 | 最终决策 |
| :--- | :--- | :--- | :---: |
| **方案 A：画布级全局回边循环** | 图逻辑完全在顶层展开 | 破坏 Kahn 算法的 DAG 契约，拓扑排序失效，死循环排查成本极高 | ❌ 放弃 |
| **方案 B：节点级内聚 ReAct 循环** | 保护核心调度引擎稳定性，迭代边界清晰，可单测性强 | 节点内部循环细节需要通过事件向调试器展开 | ✅ **采纳** |
| **方案 C：嵌套动态子画布** | 灵活性高 | React Flow 嵌套多实例性能开销大，渲染状态同步复杂 | ❌ 留待长期探索 |

### 关键实现剖析
1. **多模态工具路由执行器**：
   - `builtin_code`：交由既有的安全 Web Worker 沙箱环境执行；
   - `builtin_http`：动态组装 Payload 并发起跨域请求；
   - `canvas_node`：递归委托调用图中现有节点，实现无代码节点能力的二次复用。
2. **循环与子流程原语**：
   - 增加 `LoopNode` 支持对动态数组变量进行分批并发映射迭代；
   - 增加 `SubWorkflowNode` 为大型工作流提供嵌套封装能力。

## 3. 极限场景验证与质量指标

为防止边界场景下的系统脆弱性，作者编写了针对性的极限用例（详见 `tests/agent-node.node.test.ts`）：
- **死循环与上限熔断测试**：模拟永远无法满足结束条件的工具调用，验证 `maxIterations` 能否在指定轮次安全强行截断；
- **JSON 碎片拼装健全性**：验证大模型在分片极小的网络波动下，`delta.tool_calls` 参数拼装无任何字符错位与丢包；
- **非数组与异常输入容错**：构造空字符串、非标准 JSON 字符串作为 Loop 节点输入，验证引擎降级兜底机制。
